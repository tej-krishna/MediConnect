## Phase 5 — Doctor, Hospital and Clinic Workflows

- [x] 5.1 — Provider staff membership (`src/modules/providers/providerStaff.model.ts`/`.service.ts`): owner invites an existing registered user by email, invitee accepts, owner can remove; `isProviderMember()` (owner OR active staff) gates schedule management everywhere below, while the Phase 3 verification actions (documents, submit, listing-info, admin transitions) stay owner-only. - [x] 5.2 — Appointment slots (`src/modules/scheduling/slot.model.ts`/`.service.ts`): a provider member creates discrete bookable slots (start/end time, capacity) rather than a recurring weekly schedule (a deliberate scope choice — see ARCHITECTURE.md); only possible for an actively-verified provider. A public `GET .../slots/available` (authenticated, any user) lists only future, open, not-yet-full slots; the owner/staff view (`GET .../slots`) shows everything including past/cancelled/full. Cancelling a slot is blocked while it has active bookings.
- [x] 5.3 — Appointment booking (`src/modules/scheduling/appointment.model.ts`/`.service.ts`): `POST /appointments` atomically reserves one unit of slot capacity and creates the booking inside a single MongoDB transaction, so concurrent booking requests for the same slot can never oversell it; a partial unique index on `(slotId, patientId)` prevents the same patient double-booking the same slot while still allowing rebooking after a cancellation. Cancellation (by the patient or a provider member) reverses the capacity reservation in the same transactional pattern. Rescheduling is cancel-then-rebook rather than a dedicated endpoint (documented as a deliberate simplification, not an oversight).

## Phase 9 — Medical Records and Caregiver Access

- [x] 9.1 — `medicalRecords` module: `MedicalProfile` (blood type, allergies, chronic conditions, current medications — one per patient), `MedicalDocument` (patient-uploaded prescriptions/reports/discharge summaries/other, through the same private `StorageAdapter` pattern as every other sensitive-document flow in the app), and `VisitRecord` (manually logged visit history). All three are reached through one consistent route shape — `/medical-records/:patientId/...` where `:patientId` is the literal `"me"` or another user's id — rather than separate self/caregiver endpoints.
- [x] 9.2 — `CaregiverAccess` grants: a patient invites an existing registered user (same "must already have an account" pattern as Phase 5 provider staff) by email with a chosen subset of four scopes (`view_profile`, `view_documents`, `view_visits`, `manage_profile`) and an optional expiry; the caregiver must explicitly accept before any access exists. `assertAccess()` (`medicalRecords.access.ts`) is the **one** authorization gate every read/write in this module goes through: self always passes; anyone else needs an `active`, non-expired grant with the specific scope the action requires — computed at read time the same way provider verification expiry is (Phase 3), not via a background job. - [x] 9.3 — `RecordAccessLog` records every caregiver (never the patient's own) read of profile/documents/visits, viewable only by the patient themselves — a caregiver can never see who else has accessed the same records. ## Phase 11 — Admin, Revenue and Platform Operations

- [x] 11.1 — New `admin` module: user listing/search (`GET /admin/users`, filterable by role/status/name/email) and suspension (`PATCH /admin/users/:id/status`, `super_admin`-only) — suspending immediately revokes every one of that user's refresh tokens (reusing the exact `RefreshToken.updateMany(..., revokedAt: null)` pattern from Phase 2's password-reset flow), so the account is locked out of its *current* session, not just future logins. A `super_admin` can never suspend themselves or another `super_admin` — the only way to remove platform-admin access is direct database access, not a UI action, which is a deliberate floor against a compromised or malicious admin account locking out every other admin. This phase also built the **provider-application review UI that never existed before** — every approval from Phase 3 through Phase 10 happened via raw API calls during manual verification, because the backend review queue (`GET /providers/admin`, `POST /providers/admin/:id/transition`) never had a frontend consumer. `AdminProviderApplicationsPage`/`AdminProviderApplicationDetailPage` close that gap: a filterable queue, document download, and the full `start_review → approve/reject`, `approved ⇄ suspended` decision flow with a required reason field for reject/suspend.
- [x] 11.2 — New `analytics.service.ts`: `GET /admin/analytics/overview` aggregates gross revenue and order counts per provider type across every `totalAmount`-bearing resource (pharmacy orders, diagnostic orders, equipment/home-care requests — Phase 5 appointments and Phase 7 camp registrations are counted for volume but have no captured fee, so they're reported separately as booking counts, not revenue), via a `$lookup`-based aggregation that excludes cancelled records so gross figures reflect real fulfilled activity. `CommissionRule` (`commissionRule.model.ts`/`.service.ts`) lets an admin set a per-provider-type percentage (`PATCH /admin/commission-rules/:providerType` — `PATCH`, not `PUT`, for the same consistency reason the Phase 9 medical-profile endpoint is `PATCH`), and the overview multiplies each provider type's gross revenue by its configured rate to report a commission amount. A new `payments` module adds the `PaymentProvider` interface (`payment.interface.ts`) — the seam a real gateway (Razorpay/Stripe) plugs into later, exactly the same pattern as `StorageAdapter` (Phase 0) and `NotificationService` (Phase 2) — with `ManualPaymentProvider` as the only implementation today, since no gateway credentials are configured anywhere in this codebase. It never claims to move money or verify a webhook signature; `verifyWebhookSignature()` always returns `false` because there is no real webhook source to verify against.
- [x] 11.3 — `Transaction` ledger (`transaction.model.ts`/`.service.ts`): staff can open a refund (`POST /support/tickets/:id/refund`) only against a `refund_request`-category ticket, which records a `pending_manual_review` transaction via the manual payment provider — it does not and cannot execute a real refund. A `super_admin` settles it afterward (`POST /admin/transactions/:id/settle`, outcome `completed`/`rejected`) once a human has actually processed the refund outside the platform; the UI states this plainly rather than implying the button itself moves money. `NotificationService` (Phase 2) gained a general-purpose `notify(userId, subject, body)` method — still log-only, no real provider configured — wired into provider-verification decisions, delivery-partner review outcomes, and support-ticket resolution, so every module that makes a decision about a user now tells them through the one seam rather than each inventing its own. A new `AuditLog` (`auditLog.model.ts`/`.service.ts`) records every provider-verification decision, delivery-partner review, support-ticket resolution/closure, user suspension, commission-rule change, and transaction settlement — not a general activity feed (routine reads are already covered by request-level winston/morgan logging), specifically the highest-stakes admin/staff decisions, viewable at `GET /admin/audit-log`.
